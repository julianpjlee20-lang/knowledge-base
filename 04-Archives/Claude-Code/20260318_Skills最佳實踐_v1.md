# 製作 Skills 的最佳實務整理

日期：2026-03-18
來源：Ju 提供之技能製作筆記整理

## 一句話總結
Skills 最有價值的地方，不是把流程寫死，而是把「高訊號知識、常見陷阱、可重用腳本、分層參考資料」整理成能被模型在對的時機讀取的工作包。

## 核心重點

### 1) 不要陳述顯而易見的內容
- 模型本來就知道的一般常識、標準工程流程、過度基礎的說明，價值不高。
- 應優先放入能改變模型預設行為的知識，例如：特殊設計品味、內部慣例、非直覺規則。

### 2) 建立 Gotchas 區塊
- 這通常是整個 skill 訊號最高的部分。
- 每次模型踩坑，就補一條。
- 適合記錄：捨入規則、測試模式例外、ID 欄位差異、TTL、hook 行為等。

### 3) 技能是資料夾，不只是 SKILL.md
- 用資料夾結構做漸進式揭露。
- `SKILL.md` 做入口與路由。
- 其他 markdown / scripts / assets / references 檔案，依症狀或任務再讀取。
- 例如：
  - `references/api.md` 放詳細 API
  - `assets/template.md` 放輸出模板
  - `scripts/` 放可直接用的腳本

### 4) 不要把模型限死
- 避免把技能寫成機械式 step-by-step 菜單。
- 更好的寫法是描述目標、約束與成功條件。
- 讓模型根據情境選擇具體做法。

### 5) Description 是觸發條件
- description 不是寫給人看的 marketing copy。
- 它是給模型判斷「什麼時候該用這個 skill」的。
- 最佳寫法：直接寫出觸發詞、任務意圖、常見說法。

### 6) 用 config.json 做設定快取
- 若技能需要個人化設定，可在第一次使用時向使用者提問。
- 問完後寫入 `config.json`。
- 之後直接使用既有設定，減少重複問答。

### 7) 保留技能自己的記憶
- 若技能需要跨次執行延續上下文，可把資料寫到 `${CLAUDE_PLUGIN_DATA}`。
- 不要把需要持久化的資料存在 skill 本體目錄，升級時可能被清掉。
- 可用格式：append-only log、JSON、SQLite。

### 8) 給模型可組合的程式碼
- 提供現成函式、查詢腳本、資料清理邏輯。
- 讓模型把 token 花在判斷與分析，而不是重寫 boilerplate。
- 關鍵思路：組合，而非重建。

### 9) 按需掛鉤（On-Demand Hooks）
- 某些保護措施不適合全域常駐，但在特定任務非常重要。
- 例如：
  - `/careful`：阻擋危險 bash / SQL / force push
  - `/freeze`：限制只可改特定目錄
- 適合在 skill 觸發後只於該會話啟用。

## 延伸觀念

### 團隊共享方式
- 小團隊：直接簽入 repo 的 `.claude/skills`
- 大團隊：透過 plugin marketplace 分發，讓成員自行安裝

### 市集治理
- 不要過早中央化，但需要某種策展機制。
- 否則很容易充斥重複、低品質技能。

### 技能組合
- 技能可以互相引用。
- 例如：CSV 產生 skill 搭配檔案上傳 skill。
- 目前依賴管理不是原生能力，需靠命名與約定。

### 衡量技能效果
- 可用 hooks 記錄 skill 使用率、命中率、觸發情境。
- 這有助於淘汰不好用的 skill，或優化 description / gotchas。

## 實務結論
- 最好的 skill 通常不是一開始就很完整。
- 比較有效的演化方式是：
  1. 先用最小版本上線
  2. 收集模型常犯錯誤
  3. 補 gotchas / references / scripts
  4. 持續迭代 description 與結構

## 可直接拿來用的 checklist
- [ ] description 是否明確寫出觸發條件？
- [ ] 是否有 Gotchas 區塊？
- [ ] 是否把細節拆到 references / assets / scripts？
- [ ] 是否避免過度僵化的 step-by-step？
- [ ] 是否有需要持久化的 config / logs？
- [ ] 若有記憶需求，是否用 `${CLAUDE_PLUGIN_DATA}`？
- [ ] 是否提供現成腳本或函式讓模型直接組合？
- [ ] 是否有只在必要時啟用的 hooks？
- [ ] 是否規劃分享、策展與成效追蹤方式？
